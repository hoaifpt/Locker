# Realtime Notifications with SignalR

## Goal

Replace seeded and mocked web notifications with notifications generated by real business events, persisted in MongoDB, and delivered to authenticated web clients in real time through SignalR.

This scope covers the backend and web application. Flutter keeps its existing API and Firebase Messaging flow.

## Scope

The first implementation sends notifications for these events:

- A SePay wallet top-up changes from `Pending` to `Completed`: notify the wallet owner.
- A delivery request is created for a registered receiver: notify that receiver.
- A user creates or updates feedback: notify every user in the `Admin` role.

The implementation removes notification seed generation from `DbSeeder` and removes the web notification dropdown's dependency on `SEED_NOTIFICATIONS`. Existing persisted notification records are not deleted automatically.

## Architecture

### Persistence and delivery

MongoDB remains the source of truth. SignalR is a realtime delivery channel, not the notification store.

Application handlers use one notification service abstraction. The service:

1. Creates and persists a `Notification` record.
2. Maps the persisted record to `NotificationDto`.
3. Publishes `NotificationReceived` to the intended SignalR recipient.
4. Returns the persisted notification when the caller needs it.

Persistence happens before publication. If publication fails after persistence succeeds, the business operation is not rolled back. The notification remains available through the REST API and is recovered by the client on reconnect or reload.

### SignalR hub and authorization

The backend exposes an authenticated hub at `/hubs/notifications`.

- Every authenticated connection joins `user:{userId}`.
- The hub derives identity and role only from validated JWT claims; clients cannot choose arbitrary groups.
- The JWT bearer configuration accepts `access_token` from the query string only for the notification hub path, as required for browser WebSocket/SSE connections.

User notifications are published to `user:{userId}`. Feedback notifications are stored once for each current Admin account, and each persisted DTO is published to that Admin's `user:{adminId}` group. Each Admin therefore receives the correct notification ID and has an independent read state in MongoDB.

## Backend Integration

### Shared notification service

Introduce an application-facing notification service with operations for a single user and for Admin recipients. Its infrastructure implementation depends on `INotificationRepository`, `IHubContext<NotificationHub>`, and the identity service used to resolve Admin accounts.

The service owns DTO mapping and SignalR event naming so business handlers do not depend on SignalR details.

### Business events

- `SepayProcessIpnCommandHandler` emits the wallet notification only after the payment and wallet transaction have been completed. Duplicate IPNs that find an already completed payment return without creating another notification.
- `CreateDeliveryRequestCommandHandler` replaces its direct repository write with the shared service.
- `UpsertMyFeedbackCommandHandler` notifies Admins after the feedback upsert succeeds. The message indicates whether feedback was submitted or updated when that distinction can be determined reliably; otherwise it uses neutral wording.

### Existing REST API

The existing endpoints remain authoritative for initial state and read-state mutations:

- `GET /api/notifications/my`
- `POST /api/notifications/{id}/mark-as-read`
- `POST /api/notifications/mark-all-as-read`

No seeded fallback is returned when the API fails.

## Web Integration

Add the official `@microsoft/signalr` client and a small notification API/realtime layer.

The notification dropdown:

1. Loads persisted notifications from the REST API for the signed-in user.
2. Starts one authenticated SignalR connection.
3. Prepends `NotificationReceived` items while preventing duplicate IDs.
4. Calls the REST API when one or all notifications are marked read, then updates local state only after success.
5. Re-fetches notifications after SignalR reconnect to recover messages missed while offline.
6. Stops the connection on unmount or logout.

The dropdown shows loading, empty, and retryable error states. It does not synthesize notifications or default to a mock user ID.

## Failure Handling

- Database write failure: no realtime event is emitted and the originating handler follows its normal failure path.
- SignalR publish failure: log the error without reversing the already completed business transaction or deleting the persisted notification.
- Initial REST load failure: show an error and retry action; do not show seeded data.
- Connection interruption: SignalR reconnects automatically and the web client reloads the REST list after reconnect.
- Expired access token: connection failure follows the application's existing authentication behavior; no token is logged or embedded in notification data.

## Data and Privacy

Notification payloads contain only the fields already exposed by `NotificationDto`: ID, title, message, read state, and creation time. They do not contain access tokens, payment secrets, feedback contents, or unnecessary personal identifiers.

Feedback notifications may state that new feedback is available and include its rating/topic when appropriate, but must not broadcast the full free-text feedback content.

## Manual Verification

No seeded or mocked notification is accepted as evidence. Verification uses real local API operations and two authenticated browser sessions where needed.

Scenarios:

1. A fresh user with no records sees an empty dropdown.
2. A completed SePay top-up appears immediately for its owner and remains after refresh.
3. A delivery request appears only for the registered receiver.
4. Creating and updating feedback appears for Admin sessions but not ordinary users.
5. Mark-one and mark-all persist after refresh.
6. Disconnecting and reconnecting SignalR recovers missed records from the REST API without duplicates.
7. Replaying an already processed SePay IPN does not create a second notification.

## Out of Scope

- Replacing Flutter Firebase Messaging with SignalR.
- Deleting existing notification records from MongoDB.
- Adding an outbox, message broker, or multi-node SignalR backplane.
- Creating notifications for business events beyond the three listed above.
